# ADR-0027: 宿主兼容门语义与 peer 显式钉策略

## Status

accepted（2026-11-23，Session 41；S41 阶段 0 独立审核应清项 2、10）

## Context（背景）

SOP、ADR-0023 与 README 都把风险描述成「官方桌面每升一版，预发布版本不在插件兼容域时会被 peer
门拦下」。宿主兼容门的实际代码是 `semver.satisfies(runtimeVersion, requirement, { includePrerelease: true })`
（`packages/boot/app-boot/src/plugin-compatibility.ts:77`），预发布版本参与范围判断。实测矩阵
（`docs/sessions/audit-logs/2026-11-23-s41-stage0-audit-of-s40.md` f 项）显示：0.2.1-rc.5、0.2.2-rc.1、
0.2.2-rc.5、0.2.3-alpha.2 在宿主门语义下全部被放行，在 node-semver 默认语义下全部为假。

也就是说，官方桌面的自动更新不会把插件挡在门外，而是把未经演练的宿主直接放到插件脚下。真实风险
不是「拒装」，而是「静默运行在未演练的宿主上」。SOP 的版本决策树只写了 `semver.satisfies(V, 域)`，
没有指明用哪种语义，同一个版本在两种语义下会走进相反的分支。

项目早有先证：S38 的 satisfies 矩阵记录了 0.2.1-rc.0「npm false / gate true」，但未被 SOP 吸收。

## Decision（决策）

兼容性声明以「已演练并显式钉」为准，不以宿主门放行为准。

1. peer 范围里的显式预发布钉是「本版本已演练」的声明。宿主门放行某个版本不构成兼容性声明。
2. SOP 的版本决策同时报告两种语义的结果：默认语义为假表示该版本尚未演练，须先演练再显式钉；
   默认语义为真且宿主门语义为真表示在已声明的域内。
3. 本 session 演练 0.2.2-rc.5，并向六个 peer 范围追加显式钉 `0.2.2-rc.5`。
4. 勘正 ADR-0023 的拒装前提与其「桌面 host 协议版本目前为 4」的陈述；在 ADR-0023 的 Status 加注指向本决策。
5. SOP 的监测辅线改为读取 upstream 远端内容，不再读取本地钉死的检出文件。
6. 新增契约测试锁定 peer 范围：对已演练版本在两种语义下均为真，对域外版本在两种语义下均为假。

## Rationale（理由）

- 风险模型与代码一致，才能把有限的演练人力放到真正会出事的地方。
- 双语义并报消除了决策树的歧义，也让「显式钉」有明确的含义。
- 把范围锁进测试，之后每次扩钉都要同时面对两种语义，而不是靠目测。

## Alternatives Considered（被排除的方案）

### 方案 A: 只依赖宿主门的放行，不再显式钉预发布
- **优点**: peer 范围更短。
- **缺点**: 失去「哪些版本演练过」的记录；使用默认语义的工具链会报告 peer 不满足。
- **排除理由**: 显式钉是本仓自 S32 起的既定做法，且承担兼容性声明的职责。

### 方案 B: 把 peer 范围改成能覆盖全部 0.2.x 预发布的写法
- **优点**: 不必逐版扩钉。
- **缺点**: 等于对未演练版本预先声明兼容，与本仓「先演练后声明」的纪律相反。
- **排除理由**: 未演练的版本不该出现在兼容域里。

## Consequences（后果）

### 正面后果
- 上游每出一个预发布版本，SOP 会明确提示「宿主会放行，但尚未演练」，而不是给出「会被拦下」的错误安全感。
- peer 范围由测试守护，范围描述与 `package.json` 不再漂移。

### 负面后果 / 风险
- 每个要支持的预发布版本都需要一次演练与一次扩钉 → 这是刻意的成本，演练记录本身就是交付物。
- 尚未演练的 0.2.x 预发布宿主仍会被宿主门放行 → 在用户文档中提示升级后自查，并靠 ADR-0024 的守卫
  对缺失宿主面保持安全。
