> 本文件是 session 治理规范的**权威本体**，安装时并入目标项目（独立文档 `docs/governance-sessions.md`，
> 或并入既有治理文档并**保留 §3.1.1 / §3.4 小节编号**——接力指令头行逐字引用这两个编号，改号须同步
> 所有模板中的引用）。与本套机制相关的其他载体（`.session-start`、session 记录模板、各 references）
> 均为衍生速查；**不一致时以本文件为准**。

> 来源：从实战 30+ session 的项目治理规范泛化移植（2026-08），源项目专属物已占位符化。

## §3 Session 硬约束

dsh-websearch 是**跨 session 接力开发**的项目——每个 session 是一个独立的工作单元（可能是人，可能是
AI Agent）。没有 session 纪律，进度会断裂。

### §3.1 进入 session（接续）

**每个 session 开始的第一件事是恢复上下文，不是直接写代码：**

```bash
# 1. 读最新 session 记录（了解上一轮做了什么、遗留什么）
ls -t docs/sessions/ | head -1   # 取最新
# → 读 docs/sessions/YYYY-MM-DD-session-NN.md

# 2. 确认运行环境（硬约束，按项目约定）
node --version && pnpm --version   # 要求 node >= 22.19（本机默认 v20，先切 nvm）

# 3. 读当前阶段 progress（了解阶段目标、阻塞、下一步）
ls docs/progress/                 # 找当前 active 阶段
# → 读 docs/progress/progress-<phase>.md

# 4. 读最新规范（距上次 >7 天时）：AGENTS.md / 本文件 + docs/dont-do.md（新增条目）
# 5. 状态四问：当前阶段？进行中/阻塞？上次遗留？下一步从哪开始？
```

#### §3.1.1 前序 Session 审核确认（新任务推进前置 gate）★

**每个新 session 在开启新任务执行推进前，必须优先对前一个 session 的任务执行做系统性审核确认**
（阶段 0，见 §3.4 六阶段流程）。审核必须由**独立 Agent** 执行（与上一 session 的执行 agent 上下文
隔离，禁止自我审核），并产出三类结论：

| 债务分级 | 处置要求 | 时点 |
|---|---|---|
| 🔴 **阻塞性技术债务**（影响正确性/安全性/可测试性的缺陷） | **必须先修复，才允许推进新任务**——技术债务不清，不推进新功能 | 本 session 阶段 0 |
| 🟡 **非阻塞但必须完善的债务** | 本轮新任务推进前**优先处理**（先债后新） | 新任务开工前 |
| 🟢 **可与其他任务同步完善的非阻塞项** | 允许延后，但**必须在计划、交付物、git 提交说明中显式声明**（防隐性遗漏影响最终交付） | 归属明确的后续 session |

**🟡/🟢 判别式**：🟡 = 位于当前 WBS 验收路径上，或已有半成品实现但契约未闭环；🟢 = 完全未实现且
归属明确的后续阶段。**拿不准时归 🟡**（fail-closed，宁可多修不可漏修）。

处置要求：

- 审核基于**代码与测试实测**（file:line 证据 + 实跑），不只信上一 session 记录的"已完成"声称。
- **测试面增量采信制**：本 gate 不跑全量测试（全量测试是阶段 4 的唯一责任点，每 session 至多
  1 次）——`git diff` 判定上 session 收官以来无产品代码变更 → 采信上轮基线链 + 抽样冒烟；
  有变更 → 实跑 diff 关联测试子集。重负载命令（全量测试 / coverage / build / 类型检查 /
  lint 等大负载验证）一律串行执行，禁止并发（实测：测试与类型检查并发互相干扰——时序敏感
  测试偶发红、瞬态文件击穿类型检查输入集）。
- **审核范围同时覆盖流程合规**：上一 session 记录是否按模板齐全（生效边界内的两新节）、接力指令
  是否为当期格式（最小自举集 + 指针；兼容期内旧版全文格式同样认可）、六阶段留痕是否存在、
  audit-log 参数头是否指向当期骨架库版本、多载体重复誊写与悬空引用抽查——缺项按 🟡 记入本
  session 前置债务并补救。（这是机制性兜底：上一轮的违规会被下一轮的 gate 发现并回收。）
- **审核结论必须落盘到本 session 记录的「前序 Session 审核确认」节**（模板已含）。
- 目的：避免阻塞性技术债务给项目推进与交付带来不可逆损害；确保遗留债务始终显式、可追踪。

**禁止**：跳过这一步直接开始写代码。你会重复上一轮的坑、破坏上一轮的决策。

### §3.2 退出 session 前必须完成的 6 件事（6 件套）

**每个 session 退出前，必须落盘以下 6 类信息，缺一不可（载体可按项目规模合并——如小项目
progress 并入 session 记录尾部；信息类别本身不可缺）：**

| # | 动作 | 落盘位置 |
|---|---|---|
| ① | **可交付物落盘** | 代码 / 文档实际文件 |
| ② | **session 记录** | `docs/sessions/YYYY-MM-DD-session-NN.md`（用 session 记录模板，**含开篇「前序 Session 审核确认」节 + 底部「开发规范强化说明」节**——即"两新节"） |
| ③ | **progress + STATUS 更新** | `docs/progress/progress-<phase>.md`（任务表 + 债务台账 + 已验锚点台账）；`docs/STATUS.md` 台账行 ✅ + 当前位置块刷新 + roadmap 同行 ✅——三者同一原子收尾动作内完成，**禁止在任何工件尚未落盘时提前预写收官状态**（悬空引用） |
| ④ | **踩坑沉淀** | `docs/rca/rca-<topic>.md`（若重大）+ 更新 `docs/dont-do.md` |
| ⑤ | **CHANGELOG 更新** | `CHANGELOG.md`（仓库根——本项目为可发布 npm 包，按治理根形态探测规则落仓库根；本轮条目 + 诚实标注遗留项） |
| ⑥ | **跨 Session 接力指令** | session 记录「下一 Session 启动指令」节 + 回复末尾输出下一 session 可复制启动指令（取自 `docs/session-roadmap.md` 下一个 ⏳ 行）。**指令必须为当期格式**（最小自举集 + 指针，五语义点不得缺，见下方格式节），禁止退化为单行格式 |

#### 接力指令当期格式（最小自举集 + 指针）

```
启动 Session {{NN}} = {{目标一句话，≤2 行；WBS/验收标准见 roadmap ⏳ 行}}：
按 docs/STATUS.md 定位，依 .session-start + governance §3.1.1/§3.4 推进：计划期
（前序审核 gate 三分级 → 计划 + 独立审核 → 人工终审批准 session 计划包）→ 执行期自主
（六阶段逐一 TDD 禁批量，机械豁免除外；审核/二次确认/交叉验证独立 Agent；五禁止；高危
命令先问）→ 收尾 6 件套 + STATUS 更新 + 接力指令。
```

最小自举集五语义点（措辞可微调，语义不得缺）：①治理文档指针（.session-start + governance
编号）②计划期存在性与阶段 2.5 人工终审③六阶段 + 独立 Agent 分离 + 逐一 TDD 禁批量（机械
豁免例外）④五禁止存在性⑤高危命令门控存在性。结构纪律：头行目标 ≤2 行、止于「：」；最小
自举集单段到底（分号连接）；句号即结束，不追加独立尾行；WBS 与证据链不内嵌（指针纪律——
正本在 roadmap ⏳ 行 / session 记录 / audit-log / progress 台账）。
生成规则：从 roadmap 下一个 ⏳ 行取 Session 编号 + 目标一句话套入格式；截断兜底：以
`.session-start`「跨 Session 接力格式」节为准重新生成。**本节格式块为唯一权威本体（单源）**；
`.session-start` 与 session 记录模板中的格式块为功能副源（截断兜底 / 每 session 工作副本），
与本体不一致时以本节为准并回写修正。
**兼容期声明（项目自填）**：本格式自 2026-09-02 起生效；本项目为全新安装，无旧格式历史
session，不存在兼容期存量。

**禁止（硬红线）**：
- **无 session 记录结束 session**——下一轮无法接续。
- **无 progress 更新就切换阶段 / 跨阶段跳跃**——阶段切换必须有 progress 文档的状态变更 +
  验收证据；上一阶段验收未过，禁止开启下一阶段。
- **踩坑不沉淀**——同样的坑踩两次是治理失败。任何超过 15 分钟才解决的问题、或导致回滚/数据丢失
  的事故，必须写 RCA 或至少在 `docs/dont-do.md` 加一条。

### §3.3 Session 文档命名

- session 记录：`docs/sessions/YYYY-MM-DD-session-NN.md`；`NN` 从 `01` 起全局递增，**不按阶段重置**；
  同日多 session 用不同序号。
- 配套命名速查：plan `docs/plans/YYYY-MM-DD-NNN-<slug>-plan.md`；ADR `docs/decisions/adr-NNN-<topic>.md`；
  progress `docs/progress/progress-<phase>.md`；RCA `docs/rca/rca-<topic>.md`。

### §3.4 六阶段流程与独立 Agent 分离 ★

**整个项目的开发与功能实现，要有完整的 Harness 开发思路**：避免相同错误反复犯（RCA/dont-do 闭环）、
经验沉淀、规范的版本迭代、分支管理维护、项目记忆与文档分类规范目录管理。

**多步骤任务中的审核类步骤（如"上一 session 审核"、"计划审核"、"执行 + 审核对峙"）必须各自以
独立的 SubAgent 方式推进**——避免占用主线任务窗口上下文、防止执行与审核同上下文；规划与执行
步骤由主 Agent 承担，相互隔离推进可以更准确地获取不同任务的执行结果。

#### §3.4.1 六阶段流水线

```
基于任务需要制定高质量可执行的完整任务清单
     ↓
二次审核确认任务清单具有可执行性 / 避免分析不全、片面等问题
     ↓
【阶段 2.5 人工终审：session 计划包提交用户批准——批准即授权执行期自主推进】
     ↓
逐一执行所有任务清单（必须 100% 高质量逐一执行，TDD）
     ↓
回顾 / 审核 / 测试确认所有任务高质量完整执行
  （如果还有未完成或有待完善的任务，则必须继续执行，
   直到所有任务清单 100% 高质量完成）
     ↓
交叉验证确认计划任务清单完成度，无技术债务 / 任务执行完整
  （如果任务执行不完整，则必须追问具体哪些任务未完成、
   是否继续推进未执行完成的任务；如果有技术债务遗漏任务，
   则必须继续未完成的相关任务清单任务，
   确保计划任务高质量规范执行完成）
     ↓
回顾 / 汇报总结任务执行情况，并以任务摘要形式回顾
```

| 阶段 | 内容 | 执行方 | 强制级 |
|------|------|--------|--------|
| 0. 前序审核 | 独立 Agent 系统审核前一 session 交付质量 + 技术债务状态（§3.1.1 三分级 gate；增量采信制） | 独立 Agent ×N | 强制独立 |
| 1. 计划 | plan + ADR（如涉架构决策）落盘（任务清单 T 编号 + 验证矩阵） | 主 Agent | 主 Agent |
| 2. 独立审核计划 | 审核计划可执行性 → APPROVED / NEEDS REVISION（修订后须复审至 APPROVED） | 独立 Agent | 强制独立 |
| 2.5 人工终审 | session 计划包（plan 指针 + 审核结论摘要 + 债务三级实况 + 高危命令预告 + 验证矩阵概览）提交用户批准 → 批准即授权执行期自主 | **用户（人工）** | 人工 gate |
| 3. 逐一执行 | TDD 逐一执行所有任务（100% 高质量，禁止批量执行） | 主 Agent（自主） | 主 Agent |
| 4. 回顾审核 | 核对验收标准逐条；未完成/待完善则继续执行直到 100%（全量测试唯一责任点） | 独立 Agent | 强制独立 |
| 5. 交叉验证 | 安全/契约/前瞻追问 + 实跑冒烟（采信阶段 4 数字）；不完整则追问具体缺项并继续补完 | 独立 Agent | 强制独立 |
| 6. 汇报 | 文档同步 + 合并 main + roadmap/STATUS 状态 ✅+日期 + （若完成里程碑）progress 落验收证据 + 任务摘要 | 主 Agent | 主 Agent |

> 强制级注：0/2/4/5=强制独立审核（独立 spawn，阶段间不共享上下文；同阶段复审默认续用同一
> 审核 Agent）；2.5=用户人工批准（不可由任何 Agent 代行）；1/3/6=主 Agent（阶段 1 只读探索
> 可另 spawn 只读 Agent）。弹性通道见 §3.4.6。

> TDD 适用域（流水线中的"TDD"按本域解读）：核心逻辑/算法/契约类=先写测试证红强制；
> 重构类=禁证红、现有测试保持全绿（红了=改了行为）；文档/配置/spike 类=须有验证手段且回归不红。

**并行边界**：只读探索（阶段 1 的代码摸底/多方向调研）可并行；一切写操作与任务执行必须串行逐一；
审核 Agent 各自独立 spawn，不与执行并行混跑。

#### §3.4.2 独立 Agent 分离原则

**执行 Agent ≠ 审核 Agent**——任务审核、二次确认、交叉验证必须由独立 Agent 承担（与执行上下文
隔离）；任务规划与执行由主 Agent 推进（阶段 1 只读探索可另 spawn 只读 Agent）。禁止在同一上下文
窗口同时执行与审核。

- **Why**：同一上下文窗口执行+审核会导致上下文污染，审核者倾向自我确认（"我写的当然对"），
  产生虚假审核（false-green）。
- **How**：阶段 0/2/4/5 的审核 Agent 必须独立 spawn，不共享执行 Agent 的上下文；审核 Agent 基于
  **代码实测**（file:line 证据 + 实跑测试），不只信文档声称。

#### §3.4.3 技术债优先原则

**推进新任务前，先清理阻塞级技术债务。技术债务不清，不推进新功能。**（分级处置见 §3.1.1 表格；
🟢 级延后项必须在计划、交付物与 git 提交说明中显式声明。）

#### §3.4.4 禁止行为（绝对禁止）

- ❌ **禁止虚假审核**：不基于代码实测就声称"通过"；审核必须有文件:行号证据。
- ❌ **禁止自我以为**：不基于假设写实现；必须验证或防御性处理并测试覆盖。
- ❌ **禁止跨流程任务执行**：不跳过阶段（如跳过阶段 2 独立审核直接执行）。
- ❌ **禁止批量任务执行**：不一次性写完所有代码再测；TDD 逐一执行（唯一例外：机械变更豁免，见 §3.4.6）。
- ❌ **禁止未经真实审核/确认作为信息来源**：不只信汇总文档的"已完成"声称，必须实测代码与测试。

#### §3.4.5 Session 记录底部「开发规范强化说明」节

每个 session 记录除任务交付内容外，底部必须包含该节（模板已含固定声明），逐项确认：
六阶段流程合规（逐阶段留痕，含 2.5 人工终审批准时点）/ 独立 Agent 分离（阶段 0/2/4/5 独立
spawn + 代码实测）/ 技术债务三级处置（🔴已清 / 🟡已优先处理 / 🟢已显式声明）/ 任务清单完成度
（100% 或未完成项说明）/ 高危命令门控（触发情况与用户确认时点；验证数字遵守验证矩阵与增量
采信）。目的：以显式声明强化每个 session 的规范执行留痕，防止规范流于形式。

#### §3.4.6 分级通道（S 级轻量 / Spike / 机械变更豁免）

以下三条通道是硬约束的**分类出口**而非豁免漏洞：每条都保住其对应约束防的失败模式，条件客观、
判定留痕、下轮 gate 复核。

**S 级轻量通道**：session 同时满足客观三条件——①任务清单 ≤2 项；②不涉架构决策（无 ADR）；
③不新增/变更对外契约——**自动**走轻量流程（不需 opt-in；维持性 session 如合并/纯文档/资产
录制类默认 S 级）：阶段 2 降为最小三问独立审核（验收标准可测？依赖顺序正确？有无明显遗漏面？
一句话 APPROVED / NEEDS REVISION）；**用户的明确批准等效于独立审核 APPROVED**（用户是上下文
最独立的审核者）。S 级判定与三问结论必须留痕于 session 记录，并在阶段 2.5 计划包中向用户
标注"本棒为 S 级轻量"；下一轮 gate 复核三条件是否真实满足，不满足却走了轻量 = 按 🟡 债务
处置。其余阶段（0/2.5/3/4/5/6）不减免。

**Spike 通道（探索性 session）**：目标为"验证方向/假设是否成立"的 session 可标记为 spike——
不豁免验收标准，而是**换验收形态**：session 记录必须含三节——**假设**（一句话：X 比 Y 在
〈指标〉上更好）、**验收标准**（在什么场景实测什么指标）、**结论**（成立→合并进主线并沉淀
ADR；不成立→丢弃实现，负面结论沉淀 ADR/RCA——负面发现同样有价值）。spike 产物不直接合入
main（或合入前须经阶段 4/5 独立审核）；roadmap 中 spike 行完成后的受影响后续行须同步改目标或
标注废弃。**无假设或验收标准的"随便试试"禁止走 spike 通道**——先在 plan 里写清楚再动手。

**机械变更豁免（禁止批量执行的唯一例外）**：本豁免是「五禁止之禁止批量」「阶段表阶段 3 逐一
执行」与「六阶段流水线逐一执行」三层载体中批量禁令的**唯一例外**。变更执行前先做分类：**机械
变更** = 不改变行为语义 + 单一意图 + 可由单一验证命令全量覆盖（例：符号重命名、批量 import
修正、codemod、格式化、模板脚手架生成），分类须经独立审核 Agent 确认（防"假装机械"）后，允许
批量执行 + 一次全量验证（全量测试/lint 实跑绿）+ 单个 commit，无需逐文件红绿。**行为变更**
（任何改变可观察行为的改动）维持逐一红→绿→commit 串行，无豁免。**多 Agent 并行写操作在任何
分类下均禁止**（豁免放宽的是"逐一"，不放宽"并行写"）。

#### §3.4.7 计划期/执行期两段式 + 高危命令门控

- **计划期 = 阶段 0/1/2 + 2.5**：默认在客户端计划模式中推进（只读 + 验证命令；被拦截时请求
  放行）。阶段 2.5 把「session 计划包」提交**用户批准**——五要素：plan 正本指针 / 阶段 2
  审核结论摘要 / 债务三级实况 / 本棒预计触碰的高危命令预告（对照下方清单，无则写"无"）/
  验证矩阵概览。**用户批准 = 授权执行期自主推进**。
- **执行期 = 阶段 3/4/5/6 自主推进到底**：除高危命令清单外不逐步请求人工确认。诚实披露：
  权限模式的硬切换在客户端侧（模型不能自我提权），本条为行为纪律；批准后可提示用户切换
  更宽松权限模式加速。
- **范围变更回路**：执行中发现超出批准计划的任务面（新增任务/改验收标准/换技术路线）→
  停下执行，回计划期重新过 2.5；计划内微调（吸收审核建议、验收标准不变）→ 留痕不重审。
- **高危命令清单（执行期自主的唯一例外，fail-closed）**：大范围文件删除；`git reset --hard` /
  `git clean` 带丢弃；`push --force*`；发布类动作（publish / release / PR merge）；凭据与
  密钥读写；仓库外路径写入；系统配置修改；依赖删除或大版本变更；治理产物（STATUS / roadmap /
  progress / session 记录等）删除；`curl | sh` 类网络执行。**未列举但具备高危特征（不可逆 /
  越出仓库边界 / 对外发布 / 破坏治理留痕）的命令一律先问再执行；多条命令的组合效果命中
  任一特征时，整组按高危处置（防拆分绕过）。**

#### §3.4.8 验证矩阵与增量采信（成本控制：砍重复验证，不砍独立性）

- **验证矩阵（plan 必填节）**：每个验证面一行——`验证面 | 触发时机 | 责任阶段 | 采信规则`；
  各阶段、audit-log、session 记录引用矩阵行，不重写命令与数字（誊写纪律：同一数字/行号
  清单只在正本写一次，其余载体一律指针引用）。
- **亲跑上限**：每验证面单 session 亲跑 ≤2 次（任务绿证 1 次 + 阶段 4 汇总 1 次）；全量测试 /
  coverage 每 session 至多 1 次，唯一责任点 = 阶段 4，其报告必须含命令原文 + 实测数字。
- **阶段 5 采信**：验证数字一律采信阶段 4 报告亲跑记载，只补三正交追问 + 用户路径冒烟，
  不重复阶段 4 已跑的验证面。
- **已验锚点台账（progress 必含节）**：`锚点（file:line 或基线数字项） | 所在 commit hash |
  验证来源`；后续 Agent 引用前 `git diff` 判定：文件未变 → 引用台账不重验；已变 → 重验并更新台账。
- **重负载命令串行**：全量测试 / coverage / build / 类型检查 / lint 等大负载验证相互串行，
  禁止并发（实测：测试与类型检查并发互相干扰——时序敏感测试偶发红、瞬态文件击穿类型检查
  输入集）。
- **pre-fix 红证据入正本**：证红任务的 pre-fix 失败输出关键行（失败摘要 + 退出码）内嵌
  session 记录，不得只挂 commit message。

## 特殊场景

- **紧急修复（不走完整六阶段）**——**判定标准**：影响生产可用性/安全性/数据完整性，或阻塞
  他人当前工作的事故修复；不满足的按 S 级或标准流程走。仍必须写 session 记录（可精简，但前序
  审核节与接力指令不得省）；仍必须更新 CHANGELOG；RCA 可事后补，但不超过 48 小时。**验证下限**：
  至少全量回归测试绿 + 事故场景复现验证通过，方可宣布修复完成。**回收义务**：下一个标准
  session 的阶段 0 必须对该修复补做独立审核（按三分级正常处置）；流程合规审计将紧急修复
  记录识别为豁免场景，不按六阶段缺痕误报违规。
- **换 AI 协作者**：新 AI 必须先读 AGENTS.md + 本文件 + 最新 session 记录，确认理解质量红线。
- **长时间中断（>2 周）**：重读架构文档确认理解；检查 `docs/decisions/` 有无新 ADR；跑一遍基线
  测试确认起点。
- **交接信息最小集**（如果只能传递 3 条信息给下一个 session）：① 当前在做什么（一句话+文件路径）
  ② 卡在哪里（阻塞+原因）③ 下一步第一个动作（具体命令或文件）。

## 治理同步清单（规范变更时逐一核对，防"活矛盾源"）

修改本文件任何 session 流程条款后，必须同步核对以下载体是否一致：
1. 本文件（权威本体）
2. AGENTS.md（session 流程相关节）
3. `.session-start`（启动侧速查）
4. `docs/_templates/session-template.md`（记录骨架）
5. `docs/session-roadmap.md`（使用说明中的接力指令格式）与 `docs/STATUS.md`
   （当前位置块 / 受控词表——阶段名变更时两处必须同步）
6. `docs/dont-do.md` 与 `CHANGELOG.md`（若条款源于踩坑）
7. 来源 skill（可选维护项，非项目内依赖）：若本套件由 session-governance skill 安装且变更为
   普适改进，可按该 skill 的沉淀协议回写其 references/assets——此为跨项目维护动作，项目本身
   不依赖 skill 目录存在。
8. 治理根与路径：skill 模板升级**不改已装项目**的治理根选择与既有路径（grandfathering）；
   路径类条款变更仅对新装项目生效。
