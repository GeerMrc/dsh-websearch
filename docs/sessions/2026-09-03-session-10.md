## 踩坑 / 经验

- **坑（提交态红线第二次）**：T1 批内 settings.test fetchChain 断言漏更新——commit 带
  红（计划穷举清单点名的面仍漏一文件）。当场 amend 修复。教训：**穷举清单是验收契约，
  执行序里每文件改完立即跑该文件测试**，不留到批末
- **坑（amend 打错提交）**：T2 首次 commit 因 typecheck 红未落 → 后续 `--amend` 打在
  T1 上（把 anysearch.test 掺进 T1）——**commit 前必须确认 HEAD 是本任务基点**；修复 =
  `git reset --soft` 回 T0 重排两干净提交（未推送分支安全）
- **坑（regex 机械注入）**：含 `...overrides` 展开的测试字面量不能机械注入 resolved
  缺省字段（注入点落展开后语法破坏 + settings 侧字面量本不该注入）——typecheck + 语义
  双杀后回退手改（必填字段置于展开前）
- **坑（成员插入位置）**：members 数组首轮误插 firecrawl/deepseek 之间（非尾部）——
  BUILT_IN 序 = 注册序 = GUI 卡序三处同源，拓扑断言当场红。新增成员三处顺序必须一致
- **经验（计划期「已泛化」教训）**：语法校验循环是字面量枚举而非泛化——计划轮 2 必改②
  把错误声称纠正为显式任务 + 红测试牙齿。与 S09 活端口同族：**「自动覆盖」类声称必须
  指到派生机制（Object.values/工厂），字面量枚举点一律显式任务**
- **经验（信封规格自实现）**：HTTP 200 下 `code !== 0` 是第五失败形态——单测显式覆盖 +
  wire `code: number`（上游漂移字符串判真 fail-loud 安全侧）；content→snippet 回退两形
  用例锁死优先级，补齐官方 provider 丢弃 content 的缺口
